# PRD «Линии» (Lanes) 5v5 — 04. Бэкенд

> Раздел серверной части. Правила, числа баланса (золото, цены Предметов, Таймер респауна, состав Волны крипов, HP Башен) — в `02-game-design.md`, здесь только «как сервер это исполняет». Клиент — `03-frontend.md`, цели и метрики — `01-product.md`.
> Главная развилка: **фаза 0** (офлайн, пустые слоты — боты) или **фаза 1** (онлайн 5v5). Всё, что зависит от этого решения, помечено **[Ф1]**.

## 0. Что есть в коде сейчас (стартовая точка)

Сети и бэкенда нет, всё решает клиент. Что придётся переносить в авторитетную логику:

| Где | Как сейчас | Что нужно для сервера |
|---|---|---|
| `MobileShoot.cs` | Кулдаун, урон, патроны, магазин — поля компонента; статы оружия захардкожены в `ApplyWeaponStats` (кулдаун 0,15/0,6/0,22 c, урон 1/3/2) | Статы — в общий конфиг (JSON), патроны и кулдаун считает сервер; клиент только шлёт «нажат огонь» |
| `MagicBullet.cs` | Физическая пуля на Rigidbody, 16–19 м/с, живёт 2 c; урон в `OnTriggerEnter` у стрелка; `ownerTeam = Team.Player` захардкожен | Попадание считает сервер (свип снаряда по тикам или хитскан, см. вопрос 3); сторона из сущности, не константа |
| `PlayerHealth.cs` | HP = 3 (int), `TakeDamage` локально; «респаун» — `ResetForRound` раз в раунд | HP, смерть, Таймер респауна — на сервере; клиент только показывает |
| `MatchStats.cs` | Ровно 4 актора (`ActorId` Player/Ally/Enemy1/Enemy2), защита от дублей «по кадру» | Сущности по `NetId`, событие убийства с уникальным `eventId` от сервера |
| `Team.cs` | `Player` / `Enemy` | `Neutral=0, Blue=1, Red=2` (Лес — Neutral) |
| `Round2v2Manager.cs` | Машина состояний на корутинах и `Time.deltaTime` | Фазы матча от серверного тика |
| `ShopButtons.cs` | `SetWeapon()` бесплатно, золота нет | Запрос покупки → проверка на сервере → ответ |
| `MainMenu/ItemData.cs` | Имя, цвет, иконка; нет id, всё локально | Стабильный `itemId`; это косметика инвентаря, а не Предмет матча — две разные сущности |
| `EnemyChase.cs` / `AllyChase.cs` | Raycast'ы Unity и `FindObjectsOfType` каждый кадр | Для 60–100 Крипов не годится: Крипы — по вейпоинтам Линии + пространственная сетка; боты-игроки — «виртуальный клиент», который выдаёт те же команды ввода, что и человек |
| `MobileMovement.cs` | Rigidbody, множители гравитации, coyote/jump buffer | Для предсказания на клиенте нужно одинаковое движение на клиенте и сервере → кинематический контроллер в общем коде |

## 1. Фаза 0 (офлайн с ботами): что нужно от бэка

**Честно: для игры — ничего.** Матч целиком живёт на устройстве. Что минимально полезно заложить (≈1–2 недели одного разработчика):

| Что | Зачем | Как (дёшево) |
|---|---|---|
| Аналитика матчей | Метрики `01-product.md`: длина матча, золото по минутам, покупки, винрейт сторон | AppMetrica (бесплатно, работает в РФ) — те же имена событий, что в фазе 1 (§9) |
| Удалённый конфиг баланса | Крутить числа `02-game-design.md` без релиза в стор | Статический `balance.json` на CDN/Object Storage + версия + хэш; клиент кэширует, при недоступности — вшитый |
| Крэш-репорты | Стабильность | AppMetrica crashes / Firebase Crashlytics |
| Локальный профиль | Награды за матч, статистика режима | Локально (JSON), но **в формате будущих DTO API** (§6) + `deviceId` и `matchId` (UUID), чтобы потом перенести на сервер |

Не делать в фазе 0: аккаунты, серверное хранение наград — без сервера их всё равно можно подделать, а поддерживать придётся.

**Ключевая рекомендация, если фаза 1 вероятна в горизонте ~6 мес [Ф1]:** писать фазу 0 сразу на **общем ядре симуляции** (`Lanes.Sim`, чистый C#, без `UnityEngine`), которое в фазе 0 крутится внутри клиента как «локальный сервер», а в фазе 1 переезжает на матч-сервер без переписывания. Иначе вся логика Крипов/Башен/экономики, написанная на MonoBehaviour, будет переписана второй раз. Цена: фаза 0 дольше на ~30–40% (см. вопрос 1).

## 2. Архитектура фазы 1 [Ф1]

```
 Клиент Unity ──HTTPS──► API (ASP.NET Core) ──► PostgreSQL (аккаунты, профиль, рейтинг, награды)
   │   ▲                  │  ▲   │
   │   │ тикет матча      │  │   └──► Redis (очередь матчмейкинга, реестр серверов, сессии)
   │   │ (адрес+токен)    │  │
   │   └──── Матчмейкер ◄─┘  │ отчёт матча (подписанный, идемпотентный)
   │         │ аллокация     │
   │         ▼               │
   └─UDP─► Матч-сервер (.NET, headless) × N процессов на хост ──► события ──► ClickHouse ──► DataLens/Metabase
              ▲
           Агент хоста (запуск/учёт процессов, heartbeat в Redis)
```

| Компонент | Ответственность |
|---|---|
| API | Вход (гость/VK ID/Yandex ID/Apple), профиль, инвентарь, рейтинг, награды, история матчей, штрафы, приём отчёта |
| Матчмейкер | Очередь 5v5, party, подбор по MMR/пингу, дозаполнение ботами, выдача тикета, реконнект к активному матчу. Можно модулем API на старте |
| Матч-сервер | Авторитетная симуляция одного матча: игроки, боты, Крипы, Башни, Ядро, Лес, Золото, Магазин |
| Агент хоста | Поднимает процессы матчей, сообщает свободные слоты, drain при деплое |
| Хранилища | PostgreSQL (всё «денежное» и профиль), Redis (эфемерное), ClickHouse (аналитика) |

### Сравнение вариантов стека

| Критерий | A. Свой .NET 8 headless UDP-сервер + общее ядро `Lanes.Sim` (LiteNetLib) | B. Unity headless server + Fish-Net (или Mirror) | C. Managed: Photon Fusion 2 / UGS / Edgegap / Nakama |
|---|---|---|---|
| Переиспользование кода клиента | Низкое: движение, коллизии, Крипы пишутся заново в чистом C#; карта экспортируется в коллизионный файл | Высокое: префабы, коллайдеры, NavMesh, текущие скрипты (после отвязки от UI) | Fusion — как B (тоже Unity); Nakama — только мета, матч всё равно свой |
| CPU/RAM на матч | ~1–2 мс/тик, 30–60 МБ → **8–15 матчей на ядро** | ~4–10 мс/тик, 250–400 МБ → **1–3 матча на ядро** | Fusion dedicated = как B + плата за CCU |
| Цена на 1000 CCU (порядок) | Самая низкая (§8) | ×3–5 к A по железу | + подписка за CCU; оплата из РФ иностранным SaaS затруднена |
| Контроль / античит | Полный: свой протокол, своя валидация | Полный, но пулы/физика Unity сложнее детерминировать | Хорошая лаг-компенсация у Fusion из коробки; меньше контроля |
| Регион РФ/СНГ | Любой российский хостинг | Любой российский хостинг | UGS в РФ недоступен (Unity ушла в 2022, Multiplay Hosting сворачивается); у Photon/Edgegap локации в РФ и оплата под вопросом |
| Сложность для 1–2 разработчиков | Выше на старте (свой нетворкинг), проще в эксплуатации | Быстрее до первого прототипа; дороже и тяжелее в эксплуатации, сборки сервера тянут ассеты | Быстрый старт, но вендор-лок и юр./платёжные риски |

**Рекомендация: A** — свой .NET 8 матч-сервер на LiteNetLib + общее ядро `Lanes.Sim` (netstandard2.1, собирается и в Unity, и в сервер), API — ASP.NET Core + PostgreSQL + Redis, всё на российском хостинге. Доводы: дешевле в 3–5 раз по железу, хостинг в РФ без платёжных рисков, полный контроль античита, и у команды уже есть опыт своего .NET UDP матч-сервера (CS Magic) — плюс выученные там уроки: бинарный протокол вместо текстового, сервер **сам шлёт** снапшоты (без опроса клиентом), таймеры — от тика, чистая логика — в тестируемых классах, а не в одном `Program.cs`.
**Запасной вариант: B**, если владелец хочет онлайн-прототип за 4–6 недель ценой железа и последующей оптимизации. Nakama (self-hosted) — разумная альтернатива своему API+матчмейкеру, если не хочется писать party/очереди (см. вопрос 2).

## 3. Матч-сервер [Ф1]

### Тик и что симулирует сервер

| Параметр | Значение | Почему |
|---|---|---|
| Тик симуляции | 30 Гц (33,3 мс) | Хватает для мобильного FPS с медленным TTK; 60 Гц удваивает CPU и трафик |
| Приём ввода | 30 Гц, в пакете последние 3 команды (избыточность от потерь) | Потери 2–5% на мобильной сети |
| Снапшоты | 20 Гц базово; дальние сущности — 10 Гц; Башни/Ядро — по изменению | Трафик (§4) |
| Буфер интерполяции на клиенте | ~100 мс (2 снапшота) | Плавность при джиттере |
| Буфер лаг-компенсации | 1 c истории хитбоксов (30 кадров) | Пинг до 250 мс + интерполяция |

Сервер симулирует **всё**, клиент — только ввод, предсказание своего движения и отрисовку:

| Система | На сервере |
|---|---|
| Игроки | Движение из команд ввода (тот же код, что предсказывает клиент), HP, броня, смерть, Таймер респауна (формула — `02`), появление в Фонтане |
| Стрельба | Кулдаун, патроны, перезарядка, разброс (детерминированный seed от тика), хитскан с лаг-компенсацией или снаряды (вопрос 3), нож |
| Крипы | Спавн Волн по таймеру на каждой Линии, движение по вейпоинтам, выбор цели (приоритеты — `02`), ближняя/дальняя атака, добивание (кто нанёс последний урон → Золото) |
| Башни / Ядро | Выбор цели, урон, правило «Башня бьёт игрока, атаковавшего союзного героя» (если есть в `02`), уязвимость по порядку сноса, победа по Ядру |
| Лес | Лагеря, респаун лагерей, лиш (возврат монстра) |
| Экономика | Начисление Золота (добивание, убийство, ассист, Башня, пассивный доход) — только сервер |
| Магазин | Покупка/продажа/расходники: проверка Золота, слотов, зоны Фонтана, состояния (жив/мёртв — по правилам `02`), применение статов Предмета |
| Боты | Подменяют пустые/брошенные слоты: «виртуальные клиенты», выдающие `C_Input` — у бота нет прав больше, чем у игрока |
| Фазы матча | Загрузка → отсчёт → игра → конец (Ядро / сдача / техническое) → отчёт в API |

### Бюджет CPU на матч (10 игроков + 60–100 Крипов)

| Статья за тик | Оценка (вариант A) |
|---|---|
| Движение 10 игроков (свип капсулы по статической коллизии) | 0,05–0,1 мс |
| 100 Крипов + ~20 лесных монстров (вейпоинты, поиск цели через сетку 8×8 м) | 0,2–0,4 мс |
| Снаряды/выстрелы с перемоткой хитбоксов | 0,1–0,2 мс |
| Interest management + сериализация дельт для 10 клиентов | 0,3–0,5 мс |
| **Итого** | **~1–1,5 мс из 33 мс** (3–5% ядра) |

Планируем **8 матчей на ядро** с запасом ×2 под пики (p99 тика ≤ 8 мс). Цель для нагрузочного теста — §10. В варианте B закладывать 1–2 матча на ядро.

### Лаг-компенсация выстрелов

1. Клиент в каждой команде ввода шлёт `viewTick` + `interpFraction` — какой момент мира он видел при выстреле.
2. Сервер перематывает хитбоксы игроков **и Крипов** (добивание у Крипа должно быть честным на пинге) на этот момент, делает луч от серверной позиции глаз стрелка, возвращает мир.
3. Перемотка ограничена 250 мс; у кого задержка больше — стреляет «без компенсации» (надо упреждать). Стены статичны, луч всегда проверяется по коллизии карты. Побочный эффект «убили уже за углом» на пинге неизбежен (так во всех шутерах с лаг-компенсацией) и ограничен лимитом перемотки.
4. Для снарядов (если оставляем физические пули): снаряд спавнится на сервере в момент приёма, «догоняется» на `min(RTT/2, 100 мс)` вперёд, дальше живёт в серверном времени.
5. Хит-маркер клиент рисует сразу (предсказанно), урон и цифры — по `S_HitConfirm`.

### Interest management (не слать всех Крипов всем)

| Категория | Кому и как часто |
|---|---|
| Свой игрок | Всегда, полное состояние, 20 Гц |
| Союзные игроки | Всегда; ближе 60 м — 20 Гц, дальше — 5 Гц (для миникарты) |
| Вражеские игроки | **Только если видимы стороне** (в радиусе обзора союзного игрока/Крипа/Башни и нет препятствия по сетке видимости). Иначе не отправляются вообще — защита от wallhack/maphack |
| Крипы / монстры Леса | В радиусе 40 м от игрока — 20 Гц, 40–80 м — 10 Гц, дальше — не шлём; для миникарты — «фронт Линии» (позиция и число Крипов на Линии) 2 Гц |
| Башни, Ядро | Всем, только при изменении HP/состояния (надёжно) |
| Снаряды | В радиусе 50 м, событием спавна (позиция+направление+скорость), дальше клиент летит сам |

Приоритизация: снапшот не больше 1200 байт; не влезшее уходит в следующий снапшот с ростом приоритета («накопленная важность»).

## 4. Сетевой протокол (контракт для `03-frontend.md`) [Ф1]

Транспорт: UDP через LiteNetLib. Каналы: **U** — ненадёжный последовательный (ввод, снапшоты), **R** — надёжный упорядоченный (события, команды). Формат: бинарный, little-endian, первый байт — `msgId`. Позиции квантованы (16 бит на ось в пределах карты, точность ~1–2 см), углы — 16 бит. Версия протокола в рукопожатии: несовпадение → `S_Kick(reason=UpdateRequired)`, клиент просит обновиться.

Общие типы: `NetId` (uint16), `Team` (0 Neutral, 1 Blue, 2 Red), `EntityType` (Player, Bot, CreepMelee, CreepRanged, Tower, Core, JungleMonster, Projectile), `Lane` (0 Верх, 1 Центр, 2 Низ), `itemId` (uint16 из каталога Предметов; строковые ключи и статы — в `02`), `tick` (uint32).

### Клиент → сервер

| Сообщение | Канал | Частота | Поля | Байт |
|---|---|---|---|---|
| `C_Hello` | R | 1 раз | protocolVersion, clientBuild, matchTicket (JWT от API), configHash | ~300 |
| `C_LoadComplete` | R | 1 раз | — | 2 |
| `C_Input` | U | 30 Гц | seq, clientTick, **3 последние команды** {moveX, moveY (int8), yaw, pitch (int16), кнопки (bitmask: огонь, прицел, прыжок, присед, перезарядка, нож/слот, использовать расходник)}, viewTick, interpFraction, lastSnapshotTick (ack) | ~40 |
| `C_Buy` | R | по действию | requestId, itemId | 5 |
| `C_Sell` | R | по действию | requestId, slot | 4 |
| `C_Ping` (метка на карте) | R | ≤ 1/с | тип, позиция | 8 |
| `C_Leave` | R | 1 раз | — | 2 |

Клиент **никогда** не шлёт позицию, HP, Золото, факт попадания.

### Сервер → клиент

| Сообщение | Канал | Частота | Поля |
|---|---|---|---|
| `S_Welcome` | R | 1 раз | myNetId, team, matchId, serverTick, tickRate, mapId, configHash, состав команд (ник, бот/человек) |
| `S_Snapshot` | U | 20 Гц | serverTick, lastProcessedInputSeq, **своё состояние** (позиция, скорость, HP, броня, патроны, Золото, кулдауны, слоты Предметов), дельты сущностей {netId, тип, позиция, угол, HP, флаги}, список удалённых netId |
| `S_LaneFront` | U | 2 Гц | по каждой Линии: позиция фронта, число Крипов каждой стороны |
| `S_Event` | R | по событию | `eventId` (уникален в матче, клиент отбрасывает дубли) + тип ниже |
| `S_HitConfirm` | U | по попаданию | targetNetId, урон, хэдшот, убил |
| `S_Kick` | R | — | reason (UpdateRequired, Duplicate, Cheat, ServerShutdown) |

Типы `S_Event`:

| Тип | Поля |
|---|---|
| `Kill` | killer, victim, assisters[], weapon/источник, goldKiller, goldAssist |
| `Death` / `Respawn` | netId, respawnAtTick / позиция в Фонтане |
| `GoldGain` | amount, reason (LastHit, Kill, Assist, Tower, Passive, Jungle) — для «+N» над головой; итог всё равно в снапшоте |
| `BuyResult` | requestId, ok, errorCode (NoGold, NotInFountain, SlotsFull, Dead, UnknownItem, Cooldown), новые слоты, Золото |
| `WaveSpawned` | lane, waveNo |
| `TowerDestroyed` | lane, tier, team, lastHitter |
| `CoreDamaged` | team, hp (не чаще 2 Гц) |
| `MatchPhase` | phase (Loading, Countdown, Playing, Ended), startsAtTick |
| `PlayerConnection` | netId, status (Disconnected, BotTakeover, Reconnected, Abandoned) |
| `MatchEnd` | winner, reason (Core, Surrender, Abandon, Timeout, Technical), длительность, итоговая таблица (K/D/A, добивания, Золото, урон по Башням), rewardsPending |

### Трафик на клиента (мобильная сеть)

| Направление | Расчёт | Итого |
|---|---|---|
| Вниз | снапшот ~450 Б (своё 40 + ~6 игроков × 14 + ~25 Крипов × 8 + снаряды 60 + заголовки 60) × 20 Гц + события | **~9–11 КБ/с (~80 кбит/с)** |
| Вверх | 40 Б + 32 Б заголовков UDP/IP/LiteNetLib × 30 Гц | **~2 КБ/с (~17 кбит/с)** |
| За матч 15 мин | | **~10 МБ на игрока** — указать в FAQ, для мобильного трафика приемлемо |

## 5. Матчмейкинг [Ф1]

| Тема | Решение |
|---|---|
| Очередь | Отдельная очередь «Линии 5v5», регион (по пингу до серверов, замер на входе) + версия протокола |
| Подбор | Скрытый MMR (Glicko-2) по режиму; окно MMR расширяется со временем ожидания; party считается по среднему с надбавкой за размер |
| Party | 1–5 игроков; party из 5 — в приоритете против другой party; приглашение через API |
| Время ожидания | Цель p50 ≤ 60 c, p90 ≤ 120 c |
| Дозаполнение ботами | Через 60 c (настраивается) матч стартует с доступными людьми, баланс людей по сторонам ±1, пустые слоты — боты. Матч с ботами > 2 на сторону — без изменения рейтинга (вопрос 7). На старте онлайна при < ~200 CCU в режиме ботами будет заполнена большая часть матчей — это нормально, решение продакта |
| Аллокация | Матчмейкер берёт из Redis наименее загруженный хост в регионе → агент поднимает процесс → клиенты получают `{host, port, matchTicket}` |
| Подтверждение | «Матч найден — Принять» 10 c; не принял → в конец очереди + короткий кулдаун |

### Переподключение (ключевое для мобилы)

1. Слот игрока держится **до конца матча**. Через 10 c без пакетов место занимает бот с его Золотом и Предметами (`PlayerConnection=BotTakeover`).
2. Клиент при сворачивании/смене Wi-Fi→LTE/рестарте приложения вызывает `GET /v1/matches/active` → получает новый `matchTicket` → `C_Hello` → сервер возвращает управление, присылает полный снапшот.
3. Смена IP/порта нормальна: сессия привязана к тикету, а не к адресу (но тикет одноразовый на подключение, старое соединение рвётся).
4. iOS/Android рвут UDP в фоне — клиент не держит соединение, а переподключается при возврате (`03-frontend.md`).

### Ливеры и штрафы

| Ситуация | Последствие |
|---|---|
| Отключение и возврат до конца матча | Без штрафа, если суммарно не в сети < 5 мин |
| Не вернулся (Abandon) | Поражение с потерей рейтинга (даже если команда выиграла — без награды), счётчик ливов +1 |
| Повторные ливы за 7 дней | Блок очереди нарастающий: 5 мин → 30 мин → 2 ч → 24 ч; при 3+ — «очередь низкого приоритета» с такими же |
| Команда осталась без игрока | Бот на месте ушедшего; поражение этой команды снимает с остальных часть потери рейтинга |
| Сдача | Голосование — если будет в `02` (вопрос 8) |

## 6. Аккаунты, профиль, прогрессия [Ф1]

Вход: гостевой аккаунт по устройству сразу (без экрана логина) → привязка VK ID / Яндекс ID / Apple (на iOS обязателен Sign in with Apple, если есть другие соцвходы). Токены: короткий access JWT (15 мин) + refresh; на матч — отдельный `matchTicket` (JWT, aud=match, matchId+accountId, живёт 2 мин).

| Таблица | Поля (ключевые) |
|---|---|
| `accounts` | id, created_at, nickname, provider links, banned_until |
| `mode_rating` | account_id, mode, season, mmr, deviation, matches, wins |
| `mode_stats` | account_id, mode: kills, deaths, assists, last_hits, towers, gold_earned, play_seconds, abandons |
| `matches` | match_id (PK), mode, region, server_version, started_at, duration, winner, reason, bots_blue, bots_red |
| `match_players` | match_id, account_id (или bot), team, K/D/A, last_hits, gold, items_final, connected_seconds, abandoned |
| `reward_ledger` | id, account_id, **source_key UNIQUE** (`match:{matchId}:{accountId}`), currency/item, amount, created_at |
| `penalties` | account_id, type, until, reason, match_id |

### Отчёт матча и идемпотентность наград

1. По концу матча сервер шлёт `POST /internal/v1/matches/{matchId}/result` с подписью HMAC (общий секрет с API, вне клиента) или mTLS.
2. API сверяет состав с выданными тикетами (нельзя дописать чужой аккаунт), правдоподобность (длительность, золото/мин в пределах, указанных в `02` × запас).
3. Запись в одной транзакции: `matches` + `match_players` + рейтинг + `reward_ledger`. Повтор того же `matchId` → `200 Already processed` с тем же результатом (уникальный ключ, а не «проверили, потом вставили»).
4. Если API недоступен, матч-сервер кладёт отчёт в локальный outbox на диск и ретраит с backoff до 24 ч. Клиент видит «награды начисляются» и подтягивает их из профиля.
5. Падение матч-сервера посреди матча → API по истечении тикета помечает матч `Technical`: без рейтинга и штрафов.

## 7. Античит [Ф1]

Доверие клиенту — ноль. Клиент — пульт: шлёт намерения, получает картинку.

| Угроза | Защита |
|---|---|
| Speedhack / телепорт | Позиции клиент не шлёт; сервер сам применяет ввод. Не больше 1 команды на тик (лишние отбрасываются, счётчик нарушений) |
| Скорострельность, бесконечные патроны | Кулдаун/патроны/перезарядка только на сервере по конфигу оружия |
| Aimbot / «сквозь стены» | LOS-проверка от серверных глаз; перемотка ≤ 250 мс; статистика (точность/хэдшоты выше p99.9 по режиму) → флаг на ручную проверку (фаза 2) |
| Wallhack / maphack | Невидимые враги не отправляются (§3) |
| Накрутка Золота / покупки | Золото и Предметы — только сервер; `C_Buy` проверяется: жив/мёртв, зона Фонтана, хватает Золота, слоты, известный itemId, rate-limit |
| Подмена отчёта / наград | Отчёт шлёт только сервер с подписью; награды по уникальному ключу; клиентские «я выиграл» не существуют |
| Чужая сессия / спуфинг | matchTicket привязан к matchId+accountId, одноразовый; ключ соединения LiteNetLib = тикет; повторный вход кикает старый (`Duplicate`) |
| Флуд пакетами | Лимит пакетов/сек на соединение, разбор с проверкой длины, неизвестный `msgId` → дисконнект |
| DDoS матч-серверов | Хостинг с защитой от DDoS по UDP; IP матч-сервера отдаётся только в тикете |
| Модифицированный клиент | IL2CPP + обфускация — низкий приоритет: сервер авторитетен и так |

Одни имена событий в фазе 0 (клиент → AppMetrica) и в фазе 1 (матч-сервер → ClickHouse; клиент → AppMetrica только клиентское: FPS, загрузка, UI). Общие поля: `matchId, accountId|deviceId, team, tick, minute, mode, phase(0|1), build`.

## 11. Открытые вопросы

1. **Будет ли фаза 1 и когда?** (главный). Рекомендация: решить до старта кода фазы 0. Если онлайн вероятен в ≤ 6 мес — фаза 0 сразу на общем ядре `Lanes.Sim` (+30–40% к сроку фазы 0, экономит переписывание всей логики режима). Если онлайн не планируется — писать фазу 0 обычным Unity-кодом и не закладывать сеть.
2. **Стек.** Рекомендация: A (свой .NET + LiteNetLib, общий код с клиентом). Решить: переиспользуем ли наработки CS Magic (лаг-компенсация, нагрузочный клиент, отчёт матча) — если права и владение позволяют, это экономит недели. Nakama self-hosted вместо своего API/матчмейкера — рассмотреть, если нужна party/друзья «из коробки».
3. **Физические медленные пули (16–19 м/с) или хитскан?** Для онлайна снаряды сложнее компенсировать и дороже по трафику. Рекомендация бэка: хитскан для оружия игроков (или скорость снаряда ≥ 60 м/с), снаряды оставить дальним Крипам и Башням. Решает `02-game-design.md`.
4. **Движение на Rigidbody → кинематический контроллер.** Для предсказания на клиенте нужен одинаковый код движения на клиенте и сервере. Рекомендация: заменить в режиме «Линии» (касается `03-frontend.md`).
5. **Видимость / «туман» стороны.** Даже без визуального тумана сервер не должен слать невидимых врагов (анти-maphack). Рекомендация: ввести правило обзора (радиусы — `02`), миникарта показывает только видимых.
6. **Покупка — только в Фонтане? Можно ли мёртвым?** Сервер реализует любое, но правило нужно явно в `02`. Рекомендация: только в Фонтане, мёртвым — можно.
7. **Рейтинг в матчах с ботами.** Рекомендация: рейтинг меняется, только если ботов ≤ 2 на сторону и баланс людей ±1; иначе — только награды.
8. **Голосование за сдачу.** Снижает ливы и затяжные матчи. Рекомендация: да, с минуты, которую задаст `02`, единогласно 4/5 людей.
9. **Жёсткий лимит длительности матча** (защита от бесконечных матчей ботов/AFK). Рекомендация: 30 мин → победа по сумме урона по Башням/Ядру (правило — `02`).
10. **Вход и аккаунты:** гость + VK ID/Яндекс ID/Apple — подтвердить список; хранение в РФ (152-ФЗ).
11. **Регионы:** только Москва на старте? Нужен ли Казахстан с первого дня — зависит от аудитории `01-product.md`.
12. **Окно реконнекта и бот-заменитель:** рекомендация — слот до конца матча, бот через 10 c, «ливер» — не в сети > 5 мин суммарно.
13. **Предмет матча ≠ предмет инвентаря.** Текущий `ItemData` — косметика без id. Нужен каталог Предметов режима со стабильным `itemId` в общем конфиге (источник правды — сервер, клиент сверяет `configHash`).
14. **Аналитика:** AppMetrica (клиент) + свой ClickHouse (сервер) — подтвердить; альтернатива — только AppMetrica, но тогда серверные события придётся слать через её Post API.
